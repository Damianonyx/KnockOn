# Shared model and API contract

Draft v0.1. This contract accompanies the [build brief](BUILD_BRIEF.md). Ling should translate it into shared TypeScript types and Zod schemas before Claude builds against it. These are KnockOn application interfaces, not claims about exact Univer SDK method names.

## Domain objects

| Object | Required fields |
| --- | --- |
| Project summary | `id`, `name`, `currency`, `templateId`, `revision`, `updatedAt` |
| Project | Summary fields plus `schemaVersion`, `templateVersion`, `baselineScenarioId`, `baselineFrozen`, `demo` (boolean: created from fictional demo figures), `scenarios`, `createdAt` |
| Scenario | `id`, `name`, `kind`, `parentScenarioId`, `notes`, `workbook`, `assumptions`, `calculation`, `createdAt`, `updatedAt` |
| Assumption | `inputKey`, `note`, `source` (`user` or `demo`), `confirmed` (boolean), optional `confirmedFor` (`{ unitPrice, monthlyUnits }`) |
| Calculation | `status`, numeric `inputs`, numeric/null `metrics`, and `errors` |

IDs are opaque strings generated by the server. Timestamps are UTC ISO 8601 strings. `revision` is an integer used for optimistic concurrency across the entire project. Start `schemaVersion` and `templateVersion` at 1. The initial template ID is `bakery-v1`. Currency is an ISO 4217 code chosen at project creation and shared by every scenario; currency conversion is outside this milestone.

`kind` is `baseline`, `shock`, or `response`. The baseline has no parent. A shock forks from the baseline; a response forks from a saved shock. Forking deep-copies the source workbook and assumptions using the adapter, preserving formulas and allocating workbook identifiers as required by the installed SDK. Editing one scenario must not mutate another's data.

`workbook` is the full JSON-serializable snapshot supported by the installed Univer version. Each scenario keeps its own workbook `id`; a save must send the scenario's existing id. Preserve supported formatting and formulas. The bakery template is the only accepted workbook shape initially. Validate dimensions, expected input/result mappings, formula cells, and finite numeric input types before calculation or persistence.

`inputs` and `metrics` are server-calculated projections of the workbook, returned for UI use. They are never accepted as an independent authoritative set of client results. A user's local unsaved preview comes from browser Univer; the save response replaces it with the canonical server result for that revision.

For a saved scenario, `calculation.status` is `valid` and `errors` is empty. Local calculation errors are visible in the UI. The server rejects a save with formula errors using HTTP 422, retains the previous saved scenario, and returns the invalid cell references. It must not persist a replacement containing stale metrics.

## Bakery template and fixtures

Use a stable worksheet identifier such as `model`, and map the following keys in one shared template definition. Human-readable labels belong in column A. Column B holds values or formulas.

| Key | Cell | Meaning / formula | Fictional baseline |
| --- | --- | --- | ---: |
| `monthlyUnits` | B2 | Units sold per month | 1000 |
| `unitPrice` | B3 | Price per unit | 5 |
| `ingredientCostPerUnit` | B4 | Ingredient cost per unit | 2 |
| `monthlyEnergy` | B5 | Monthly energy expense | 400 |
| `monthlyRent` | B6 | Monthly rent | 600 |
| `monthlyWages` | B7 | Monthly wages | 1200 |
| `monthlyOtherCosts` | B8 | Other monthly expenses | 100 |
| `monthlyDelivery` | B9 | Monthly supplier delivery cost | 0 |
| `revenue` | B11 | `=B2*B3` | 5000 |
| `ingredientCosts` | B12 | `=B2*B4` | 2000 |
| `fixedCosts` | B13 | `=SUM(B5:B9)` | 2300 |
| `totalCosts` | B14 | `=B12+B13` | 4300 |
| `profit` | B15 | `=B11-B14` | 700 |
| `marginFraction` | B16 | `=IF(B11=0,"",B15/B11)` | 0.14 |

The adapter maps a blank B16 result to `null`, not zero. Show `marginFraction` as a percentage in the UI. Fixtures use generic currency units; demo projects must label their selected currency and fictional figures.

| Scenario | Changes from its source | Revenue | Total costs | Profit | Profit change vs baseline |
| --- | --- | ---: | ---: | ---: | ---: |
| Baseline | Values above | 5000 | 4300 | 700 | 0 |
| Energy shock | From baseline: `monthlyEnergy = 600` | 5000 | 4500 | 500 | -200 |
| Price response | From shock: `unitPrice = 5.5`, explicitly assumed `monthlyUnits = 950` | 5225 | 4400 | 825 | 125 |
| Supplier response | From shock: `ingredientCostPerUnit = 1.8`, `monthlyDelivery = 100` | 5000 | 4400 | 600 | -100 |

These are illustrative test cases, not demand estimates. All other inputs remain equal to the source scenario. Compare numerical results with a small tolerance for floating-point arithmetic; do not compare only formatted currency strings.

All eight inputs must be finite and nonnegative. Zero is valid and is distinct from an empty required cell. The initial units field permits a nonnegative numeric monthly estimate. Formula cells and template layout are not user-editable in this version. Reject attempted changes to their definitions on the server, even if browser protection was bypassed.

When `unitPrice` changes relative to the parent scenario, the user must explicitly enter or confirm a `monthlyUnits` assumption before saving, including if they expect sales to stay unchanged. UI confirmation alone is insufficient: validate the assumption record on the backend. Changing price or units again clears that confirmation. Forked assumptions must remain visible, with inherited context shown.

Implementation: a confirmation is a `monthlyUnits` assumption with `source: "user"`, `confirmed: true`, and `confirmedFor` equal to the scenario's saved `unitPrice` and `monthlyUnits`. When the price differs from the parent's, the server rejects a save without a matching confirmation (422 `ASSUMPTION_REQUIRED`). A confirmation whose `confirmedFor` no longer matches is saved as `confirmed: false` without `confirmedFor`. A `demo` assumption whose value no longer matches the demo figure, or that belongs to a non-demo project, is saved as `user`.

## Editor adapter contract

Define a small application-owned adapter instead of spreading Univer calls throughout components:

- Load/dispose the active scenario workbook.
- Read or set an input by the template's stable key.
- Observe changes and wait for recalculation completion.
- Read completed input/metric projections and cell-level errors.
- Export a supported snapshot without dropping formulas or formatting.
- Inspect a mapped result's formula and contributing input cells.

Browser and headless implementations share the template mappings and snapshot schema. They do not share browser UI imports. Verify the exact SDK APIs against the chosen Univer version during the spike. Suppress change listeners while loading snapshots so server responses do not cause save loops.

## HTTP endpoints

All endpoints use JSON. Success responses use `{ "data": ... }`. Define the corresponding types in `src/lib/contracts/`.

| Method and path | Request | Successful response |
| --- | --- | --- |
| `GET /api/templates` | None | 200: array of template descriptors with ID, version, name, description, input mappings, and simplifications |
| `GET /api/projects` | None | 200: project summaries, most recently updated first |
| `POST /api/projects` | `{ name, currency, templateId, initialData: "demo" \| "blank" }` | 201: project with one editable baseline |
| `GET /api/projects/:projectId` | None | 200: complete project including scenario snapshots and calculated projections |
| `POST /api/projects/:projectId/scenarios` | `{ expectedRevision, sourceScenarioId, kind: "shock" \| "response", name }` | 201: updated project including the new fork and incremented revision |
| `PUT /api/projects/:projectId/scenarios/:scenarioId` | `{ expectedRevision, name, notes, workbook, assumptions }` | 200: updated project with recalculated scenario and incremented revision |
| `POST /api/projects/:projectId/scenarios/:scenarioId/explanation` | `{ expectedRevision, question? }` | 200: `{ projectId, scenarioId, projectRevision, model, explanation, generatedAt, changedInputs }` |
| `POST /api/projects/:projectId/analysis` | `{ expectedRevision, minUnits, maxUnits }` | 200: `{ projectId, projectRevision, minUnits, maxUnits, scenarios }`, read-only (see "Break-even and sales sensitivity") |

The blank template starts with zero-valued inputs and zero totals, with no business assumptions inferred. The UI must state that figures have not yet been entered. Demo mode loads the fictional fixture and visibly marks it as demo data.

For each mutation, validate the project/scenario relationship, expected revision, template, input data, and relevant assumptions. Save a mutation and its revision increment atomically. A fork uses the persisted source, so the UI must save any source draft first. Creating the first shock atomically freezes the baseline. Reject writes to a frozen baseline.

Do not add a separate calculations endpoint or accept independent metric fields for scenario saves. The one exception is the read-only analysis endpoint below, which accepts only a sales range, calculates from saved inputs and writes nothing. Comparisons use returned scenario metrics; display profit change by comparing those saved values. Naming rules and reasonable payload limits should be implemented consistently in shared schemas and documented with the scaffold.

Implemented limits: project and scenario names are 1–80 characters after trimming; notes are up to 5000 characters; assumption notes up to 2000; currency is three letters and is upper-cased; request bodies are limited to 1 MB.

## Errors and recovery

Errors use this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Enter or confirm expected monthly sales for this price change.",
    "fields": {
      "assumptions.monthlyUnits": "Confirmation required."
    }
  }
}
```

Use 400 for malformed JSON/request shape, 404 for missing project/scenario/template, 409 for revision conflicts or a frozen baseline, and 422 for invalid model inputs, missing assumption confirmation, or calculation errors. Use distinct error codes such as `REVISION_CONFLICT`, `BASELINE_FROZEN`, and `CALCULATION_ERROR`.

| Status | Codes |
| --- | --- |
| 400 | `BAD_REQUEST` (malformed JSON or request shape; `fields` names each problem) |
| 404 | `NOT_FOUND` |
| 409 | `REVISION_CONFLICT` (with `currentRevision`), `BASELINE_FROZEN` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 422 | `VALIDATION_ERROR` (workbook `fields` by cell, e.g. `workbook.B15`), `ASSUMPTION_REQUIRED`, `INVALID_FORK`, `CALCULATION_ERROR` (with `invalidCells`) |
| 502, 504 | `EXPLANATION_FAILED` |
| 503 | `EXPLANATION_UNAVAILABLE` (no key, rejected key, or rate limit) |
| 500 | `INTERNAL_ERROR` | Unexpected failures return a generic 500 message without credentials or internal stack traces.

For a revision conflict, return `currentRevision` in the error object. Preserve the user's draft and offer to reload the latest saved project; never silently overwrite it. A failed or timed-out save must not show “Saved”. Retrying a save with an outdated revision must produce a conflict rather than applying an uncertain update twice.

## Explanations

KnockOn uses AntLing's Ling 3.2 Flash (`ANTLING_MODEL`, default `Ling-3.2-flash`) for explanations. The explanation endpoint only describes the current saved revision: send the `expectedRevision` you are showing, and a newer revision returns 409 `REVISION_CONFLICT`. The server sends Ling the saved inputs, formulas, Univer-calculated results, inputs changed from the parent, profit change against the baseline, assumptions with their source and confirmation, and the template simplifications. Explanations are not stored; the UI treats one as stale once the project revision changes. `changedInputs` lists inputs that differ from the parent scenario, so the UI can show what the explanation refers to without relying on Ling. The key stays on the server, and the spreadsheet remains fully usable when Ling is unavailable.

## Break-even and sales sensitivity

`POST /api/projects/:projectId/analysis` accepts `{ "expectedRevision": 3, "minUnits": 500, "maxUnits": 1500 }`. `minUnits` and `maxUnits` are whole numbers from 0 to 1,000,000,000, and `maxUnits` must be greater than `minUnits`; anything else returns 400 `BAD_REQUEST`. Ownership is checked first: unknown or unowned projects return 404. An outdated `expectedRevision` returns 409 `REVISION_CONFLICT` with `currentRevision`. The revision is checked again after calculation, so a save that lands while Univer is calculating also returns 409 instead of a result that looks current. Saved inputs that cannot be calculated return 422 `CALCULATION_ERROR`. The response uses `Cache-Control: no-store`.

The endpoint never writes: workbooks, assumptions, charts, saved results, the frozen baseline and the revision are unchanged. For each saved scenario, the server validates the stored workbook, reads its eight inputs (B2:B9) and builds one sheet of a temporary workbook that a fresh headless Univer instance calculates. Cached results and chart resources are not copied. The temporary sheet repeats the model formulas and adds analysis-only cells, which are never saved to a scenario:

| Cell | Meaning | Formula |
| --- | --- | --- |
| E2, E3 | Chosen range | `minUnits`, `maxUnits` |
| B13 | Monthly overheads | `=SUM(B5:B9)` |
| B18 | Contribution per unit | `=ROUND(B3-B4,9)` |
| B19 | Minimum whole units to cover costs | `=IF(B18>0,ROUNDUP(ROUND(B13/B18,6),0),IF(B13=0,0,""))` |
| A24… | Sampled units, row *i* of *steps* | `=ROUND($E$2+($E$3-$E$2)*i/steps,0)` |
| B24… | Revenue | `=A24*$B$3` |
| C24… | Total costs | `=A24*$B$4+$B$13` |
| D24… | Profit | `=B24-C24` |

`steps` is `min(10, maxUnits - minUnits)`, giving at most eleven samples that include both endpoints, and every whole unit for ranges under ten. The two `ROUND` calls in B18 and B19 remove binary floating-point noise, so an exact threshold is not rounded up by one (for example 15 / (4.35 − 4.05) is 50, not 51). A quotient within a millionth of a whole unit is treated as that whole unit.

Each entry in `scenarios` (ordered as in the scenario list) has `scenarioId`, `name`, `kind`, `inputs`, `fixedCosts` (B13), `contributionPerUnit` (B18), `breakEvenUnits` (B19, or `null` when no volume covers costs), `breakEvenStatus` and `points` (`{ units, revenue, totalCosts, profit, row }`, where `row` is the sample's row in the analysis sheet). `breakEvenStatus` is a label derived from the signs of B18 and B13, not a calculation:

| Status | When | `breakEvenUnits` |
| --- | --- | --- |
| `attainable` | Contribution above zero | Threshold; 0 when overheads are zero |
| `unreachable` | Contribution zero or negative, overheads above zero | `null` |
| `any-volume` | Contribution and overheads both zero | 0 |
| `zero-sales-only` | Contribution negative, overheads zero | 0 |

The client shows results only while the response's `projectRevision`, `minUnits` and `maxUnits` match the saved revision and the entered range. Unsaved edits are excluded. The sensitivity chart is drawn by the application from these Univer results; it is not a worksheet chart and is not part of printing or Excel export. Figures are IEEE double-precision numbers, so results above about 9,000,000,000,000,000 lose pence-level precision.

## Charts and Excel downloads

Worksheet snapshots now include `SHEET_CHART_PLUGIN` and `SHEET_DRAWING_PLUGIN` resources. Both must have valid JSON, matching chart IDs and anchors, and sources within this workbook's `model!A1:B16`. Up to six charts are accepted. External workbook sources and non-chart drawings are rejected. Server recalculation saves supported plugin resources, and forks remap their internal workbook references. The frozen-baseline rule also applies to chart edits.

`POST /api/projects/:projectId/scenarios/:scenarioId/export` accepts only `{ "expectedRevision": 2 }`. Ownership is checked before conversion. Unknown or unowned projects/scenarios return 404; an outdated revision returns 409. The server exports the saved workbook, never an arbitrary snapshot from the request. Frozen baselines can be exported. Export does not change the project revision.

A successful response is binary XLSX (`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`), with an attachment filename containing the project name, scenario and revision, `X-KnockOn-Revision`, and `Cache-Control: private, no-store`. Error responses retain the normal JSON error envelope: 503 `EXPORT_UNAVAILABLE` for license/runtime configuration and 502 `EXPORT_FAILED` for conversion failures. The client keeps the scenario intact and displays the failure without automatically resubmitting.
